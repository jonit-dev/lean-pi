# PRD-026 — Bundled Skill Pack

**Status:** NOT STARTED
**Complexity:** 4 (MEDIUM)
**Risk override:** none — the integrity check is a hash comparison over files shipped inside LeanPi's own npm package; it adds no trust boundary (bundled stays user-scope trusted per PRD-017, project-supplied skills stay gated), no credential, no network call and no migration.
**Owner:** joao
**Depends on:** PRD-001, PRD-005, PRD-017

## Context

**Covers:** none (new slice, product-owner request); ROADMAP §6.1, §16, §51 (Skills block, consumed not owned)

Current behavior: none. The repository is greenfield — only `docs/PRDs/v1/*.md` exists. Every path named below is created by this PRD's phases or by a dependency PRD.

PRD-005 makes the *user's installed* skill library discoverable and selectable. That is the right design for a user who already has a library, and the wrong design for everything else: on a machine with no `~/.claude/skills`, LeanPi's own PRD lane (PRD-012) cannot load `prd-creator`, cannot load `prd-manager`'s closure helper, and falls back to its built-in minimal contract — the harness silently becomes a weaker product because of something outside the package. The skills LeanPi's own lanes depend on must ship with LeanPi.

Inspected at plan time (see *External Skill Dependencies* for paths): the seven candidate upstream skill directories, their file inventories, their upstream licences, and the two facts that shape the copy rule — `~/.claude/skills/prd-creator` and `~/.claude/skills/prd-manager` are **symlinks** into `~/.agents/skills/`, and the `prd-creator` directory carries a stray `SKILL.md.bak` next to its `SKILL.md`. A naive recursive directory copy would either copy nothing (symlink not followed) or vendor a backup file into the published package.

Dependencies consumed, not rebuilt:

- **PRD-001** established vendoring as a mechanism for FR-002: a pinned copy plus a lock recording `{source, version, sha256, syncedAt}`, refreshed by `scripts/sync-ponytail.mjs` through a configurable discovery order. This PRD generalizes that mechanism to a multi-file, multi-skill pack. It does **not** re-vendor the Ponytail instruction prefix and claims no part of FR-002: the prefix stays exactly where PRD-001 put it, is not a pack entry, and is not duplicated under `skills/`.
- **PRD-005** owns the registry, JEV relevance routing, lazy body loading, `/skills`, pinning, and the root precedence project > user global > plugin. This PRD adds one new *root class* to that registry. No second registry, no second loader, no second `/skills`.
- **PRD-017** owns trust. Bundled skills ship inside the installed package and carry user-scope trust, like plugin skills; project-supplied skills stay untrusted and gated by `assertTrusted()`. This PRD redefines nothing there.
- **PRD-012** adapts `prd-creator`/`prd-manager`/`prd-executor` into the PRD lane. This PRD guarantees those bodies and that closure helper are *present on any machine*; PRD-012 consumes them through PRD-005's resolution order unchanged.

## Solution

Vendor files at sync time, verify hashes at load time, register one extra root. That is the whole design. No skill marketplace, no auto-updater, no remote fetch, no plugin API, no background process — if this grows a daemon it is wrong.

**The pack on disk.** `skills/<name>/` holds each bundled skill's `SKILL.md` plus the auxiliary files it actually needs (`scripts/`, `agents/`), one subdirectory per skill, shipped inside the published npm package via `package.json` `files`. The copy rule is a per-skill **file allowlist** (`SKILL.md`, `scripts/**`, `agents/**`), with symlinked source directories resolved through `fs.realpath` before reading — the two hazards found on the reference machine. `prd-manager`'s whole `scripts/` directory is vendored as a unit rather than tracing `prd-close.mjs`'s import graph: the scripts share a common `prd-lib.mjs`, and copying seven small files is cheaper than an import resolver.

**Initial pack**, one line of justification each:

| Skill | Why it is bundled |
|---|---|
| `prd-creator` | PRD-012's authoring contract; without it `/prd create` degrades to `skill_source: builtin-fallback` |
| `prd-manager` (+ `scripts/`) | PRD-012's `/prd close` spawns its `prd-close.mjs`; the only pack entry whose auxiliary files are executable, and the reason the pack is not single-file |
| `prd-executor` | PRD-012's Manager reads it for work-unit shape so units match what PRD-007's executor expects |
| `i-have-adhd` | Product-owner-requested output shaping, invoked explicitly; useless if absent and unobtainable from inside the harness |
| `ponytail-review` | Over-engineering review pass, the companion to PRD-001's always-on prefix |
| `ponytail-audit` | Whole-repo bloat audit, same family |
| `ponytail-debt` | Harvests the `ponytail:` markers the prefix tells the executor to leave behind — the prefix is only half a loop without it |

The `ponytail` prefix skill itself is **not** in this table. It is PRD-001's static prefix (§6.1: a versioned instruction prefix, not a discoverable skill) and is vendored once, at `src/core/instructions/ponytail.md`. `ponytail-gain` and `ponytail-help` are display-only commands and are omitted rather than shipped for completeness.

**Lock.** `skills/pack.lock.json` records, per skill: `{ name, source, version, files: [{ path, sha256, bytes }], licence, attribution, syncedAt }`. `source` is the upstream path or repository the bytes came from. `version` is the upstream declared version when one exists (plugin cache path segment or frontmatter — `i-have-adhd@0.3.0`, the ponytail satellites at `4.9.0`) and otherwise a content pin `sha256-<first 12 hex of SKILL.md>`, so every bundled skill has a reportable pinned version even though the `prd-*` skills declare none. This is the same lock *schema* PRD-001's single-entry `ponytail.lock.json` uses, extended with `files`, `licence` and `attribution` — additive, so PRD-001's `{source, version, sha256}` assertions stay literally true.

**One sync mechanism, decided.** `scripts/sync-skills.mjs` is a maintainer tool: it resolves each entry's upstream through a configurable source root (`--source` flag → `LEANPI_SKILL_SOURCE` → `$CLAUDE_PLUGIN_ROOT` / `$HOME/.claude` discovery defaults, never a literal `/home/joao` in shipped code), copies the allowlisted files, recomputes hashes, and rewrites the lock. It runs in a pull request; nothing invokes it at runtime or on install. `--check` recomputes hashes and exits non-zero on drift.

The decision the assignment demands, made rather than deferred: **the mechanism merges; the Ponytail prefix becomes the special case.** The copy/hash/lock core lives once, in `src/skills/vendor.mjs`, and `scripts/sync-ponytail.mjs` (PRD-001) is reduced to an argv wrapper that calls that core with a single-entry, `kind: 'prefix'` spec — keeping its `--check` CLI and exit codes, and therefore PRD-001's AC-8, intact while deleting its private copy/hash implementation. There is exactly one vendoring implementation in the repository. Ordering is not a constraint: if PRD-001 lands first, this PRD's Phase 1 refactors its script into the wrapper; if this lands first, the core simply already exists for PRD-001's Phase 3 to call.

**Registration.** `src/skills/pack.ts` exposes `bundledRoot()` (the packaged `skills/` directory, resolved relative to the module, not to `cwd`) and `packEntries()` (parsed lock). PRD-001's `loadConfig()` appends that root to `LeanPiConfig.capabilities.skillRoots` as the **last** entry with class `bundled`, extending PRD-005's precedence to **project > user global > plugin > bundled**. A user's own `prd-creator` therefore always wins over the bundled copy, which is the correct default: the bundled pack is a floor, not an override. `/skills` gains the source class and, for bundled rows, the lock's pinned version. Disable/enable reuses PRD-005's existing `LeanPiConfig.skills.state` — bundled skills are disableable per skill, with no new state store and no new command.

**Integrity is the supply-chain property worth having.** PRD-005's body loader calls `verifyBundledFile(path)` before returning bytes for any skill whose source class is `bundled`: hash the file, compare to the lock, and on mismatch **throw**, naming the offending path and both hashes. Not a warning, not a silent skip, not a fall-through to the next root — a load that cannot be proven to be the vendored bytes does not happen. A missing lock entry for a file inside `skills/` is the same hard failure. Registry *scanning* stays frontmatter-only per PRD-005, so the check runs on selection, where the bytes are actually read.

**Licensing is handled, not waved at.** Every pack entry carries an explicit `licence` and `attribution` in the lock; `sync-skills.mjs` refuses to vendor an entry whose licence resolves to nothing — it fails naming the skill rather than shipping unlicensed bytes. The resolution order is frontmatter `license:` → a `LICENSE` file at the upstream bundle root (copied to `skills/<name>/LICENSE` when present) → an explicit declaration in the sync spec. The verified reference upstreams are MIT: the ponytail satellites (MIT, © 2026 DietrichGebert) and `i-have-adhd` (MIT, © 2026 Ayoub Ghriss, also declared in its frontmatter). The three `prd-*` skills are the repository owner's own work and are declared first-party in the spec with attribution to `joao`. `skills/NOTICE.md` is generated from the lock, so attribution cannot drift from what actually shipped.

**No network, stated explicitly.** Nothing in this PRD fetches anything at runtime or at install time. The bundled bytes arrive by ordinary `npm install` of the LeanPi package; there is no install script, no postinstall hook, no update check, and no HTTP client on any bundled-skill code path. Re-vendoring is a human action in a pull request.

Consumer path: `npm install leanpi` → `skills/**` present in `node_modules` → session start → `loadConfig()` appends `bundledRoot()` → `scanSkills()` indexes bundled frontmatter → PRD-005 selection picks a skill → body loader calls `verifyBundledFile()` → verified bytes reach `assemble()`'s SEMI-STABLE layer.

Restated non-goals (ROADMAP §58) binding here: no blanket capability exposure — bundling changes *availability*, never selection, and an unselected bundled body reaches no context; no correctness claims without evidence; nothing here requires JEV.

## JEV Decision Sites

None — vendoring and integrity are deterministic. Copying an allowlisted file, comparing a SHA-256 to a lock entry, and ordering a root list have exactly one correct answer each, so there is nothing for a judgement site to decide and no fallback to design. Relevance selection *over* these skills is PRD-005's `skill.disclosure` site, unchanged: a bundled skill is ranked by the same pipeline as any other registry entry.

**Status:** NOT STARTED
**ACs:** AC-4, AC-6, AC-7

**Implementation:** Write the core first: given `{ name, source, allowlist, licence? }`, resolve the source directory through `--source` → `LEANPI_SKILL_SOURCE` → `$CLAUDE_PLUGIN_ROOT` → `$HOME/.claude` (discovery defaults only; no literal machine path in any shipped file), `realpath` it, walk the allowlist patterns, copy matched files, hash each, resolve the version (upstream declared → plugin path segment → `sha256-<12>` of `SKILL.md`) and the licence (frontmatter `license:` → upstream bundle `LICENSE`, copied into the pack → spec declaration). A skill with no resolvable licence aborts the whole run before any write, naming the skill. Lock entries are emitted in a stable key order with sorted `files`, and `syncedAt` is preserved when every hash is unchanged — that, not a timestamp rewrite, is what makes a second run a true no-op. `--check` recomputes hashes against the lock and exits non-zero naming the first mismatch. Run the tool once against the real upstreams to produce the committed pack, then generate `NOTICE.md` from the lock. Reduce `sync-ponytail.mjs` to the wrapper: PRD-001's lock fields are a subset of this schema, so its `{source, version, sha256}` assertions keep passing while its private copy/hash code is deleted. Nothing here runs at install or runtime; `package.json` gains no lifecycle script.

Negative controls: mutating one vendored byte makes `--check` exit non-zero (so the check is not constant), and dropping an entry from the spec makes the `npm pack` assertion fail rather than pass vacuously. Distinct risks covered: unfollowed symlink, stray file shipped, lock churn on a clean run, unlicensed bytes shipped, pack missing from the published tarball, a second vendoring implementation.
